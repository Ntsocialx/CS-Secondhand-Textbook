# Separate Admin Portal and Admin Login

## Objective

Separate Campus Exchange administration from the student marketplace frontend while
retaining the existing Express API and its server-side authorization. Create a standalone
Next.js admin application in a top-level `admin/` directory, outside `client/`. Give it a
clearly labeled **Admin login** page and keep the current student login experience labeled
and functioning as it does now.

## Scope

- Create an independently buildable Next.js admin app under `admin/`, using the established
  Next.js, React, TypeScript, Tailwind, and NextAuth credentials-provider stack.
- Move the existing admin dashboard, listing review, reports, fee periods, analytics, and
  admin navigation into the new app without dropping any existing capabilities or
  weakening their loading, empty, success, and error states.
- Give the admin app its own explicit `/login` page titled/labeled **Admin login**. Authenticate
  through the existing Express login contract using server-only `API_URL`; reject any
  authenticated account whose returned role is not `ADMIN`. Do not add a backdoor, shared
  credential, default password, or client-trusted role.
- Protect admin pages using the authenticated admin role and keep every admin API
  authorization check in Express. Preserve current admin page/API behavior and token handling.
- Keep the marketplace's existing `/login` page and student sign-in flow unchanged. Add a
  distinct, clearly labeled link to the admin app where users can find sign-in, using a
  documented public `NEXT_PUBLIC_ADMIN_APP_URL` (or equivalent) rather than hardcoding a
  production URL.
- Preserve old marketplace `/admin` links with a safe redirect to the corresponding new
  admin-app path and its Admin login when unauthenticated, if the configured admin app URL is
  present. Do not leave a second functional copy of admin pages in `client/`.
- Document local development ports, independent build/run commands, the admin app's required
  NextAuth and API environment variables, the public admin URL used by the marketplace,
  and deployment/auth-cookie considerations in `README.md`.
- Update `AGENTS.md` architecture/API notes so future admin UI changes belong to `admin/`
  and role enforcement continues to belong to the Express API.

## Security and compatibility requirements

- Do not expose database credentials, SMTP credentials, JWT signing secrets, or admin
  authorization logic to browser code.
- Use a distinct NextAuth session secret for the admin application; do not assume a
  marketplace login cookie is shared between separately deployed apps.
- Admin NextAuth must sign in only against the existing Express auth endpoint, carry the
  returned access token server-side in its session as currently done in the marketplace,
  and only establish an admin session for a returned `ADMIN` role.
- Preserve the backend's current password lockout, student-domain and consent policies.
- A student account that attempts admin login must receive a clear access-denied error, not
  an admin session or private admin data.
- Keep the admin app usable locally without exposing it through marketplace client-side role
  toggles. Document that `DATABASE_URL`, SMTP settings, and operator credentials remain
  server-only and are not supplied or generated by this change.
- Avoid unrelated redesigns, new libraries, and changes to marketplace authentication.

## Acceptance checks

1. The admin app lives at repository-root `admin/`, has its own dependencies/configuration,
   and builds independently from `client/`.
2. The admin login screen is clearly labeled **Admin login**; the student login remains the
   normal client login and registration flows are unaffected.
3. A valid `ADMIN` can sign in and access overview, listings, reports, fees, and analytics.
4. A valid `STUDENT` cannot establish an admin session or fetch admin data; signed-out users
   are sent to the admin app's login screen.
5. Express still rejects unauthorized admin API calls regardless of UI/session behavior.
6. Legacy `/admin` links redirect safely when the admin app URL is configured.
7. Client and admin builds plus targeted lint/type checks pass; document any checks blocked
   by unavailable database or deployment configuration.
